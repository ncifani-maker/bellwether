## 1. What changed
The PRD listed sponsor-trail mining as one of five discovery sources, weighted inside a single 25-point "audience purchase behavior" dimension. Homeaglow's green light moves it from one source among five to the **primary discovery mechanism** for Instance A, and this spec defines it properly: what the signal is, how it is measured, what it is not, and how it enters the score.
Everything else in the PRD holds. Approval rules, CPM caps, link logging, and the review gate are unchanged.
## 2. The signal
**Claim:** a brand that buys creator placements on performance terms and rebooks the same creator repeatedly has already run the experiment Homeaglow is about to pay for. The rebooking decision is the brand's own conversion data, made visible from outside.
HelloFresh is the highest-value donor brand for Homeaglow's category. It sells a recurring, delivered, household-convenience subscription to the same buyer Homeaglow wants, it has run creator sponsorship at scale since 2014 with roughly 800 tracked YouTube creators and about 2.7 videos per creator, and it pays on tracked code conversion rather than flat reach. A creator HelloFresh has booked nine times is a creator whose audience demonstrably buys a recurring household service through a link in a video description. That is the exact behavior Homeaglow needs and the exact thing no media kit reports and no agency screens for.
**What the signal is not.** It is not a promise of Homeaglow conversion, and it does not transfer across categories without argument. A gaming channel HelloFresh rebooks proves the audience buys meal kits; it does not prove they book house cleaning. The signal is strongest where the donor brand's purchase context and the target brand's purchase context are the same moment in the same life — household load, time scarcity, outsourcing a chore. Scoring must carry that qualifier rather than treating raw sponsorship count as the ranking.
**Secondary donor brands**, same logic, lower weight: Instacart, Thumbtack, Care.com, TaskRabbit, Handy, Shipt, Hungryroot, Factor, Rocket Money. Competitor meal kits (Blue Apron, Home Chef, EveryPlate, Gousto) count as donor evidence but flag exclusivity risk.
## 3. Measurement method
This is the part that has to be specified precisely, because the obvious way to count sponsorships is wrong.
**Do not use YouTube's channel search.** Querying a channel for "hellofresh" returns relevance-padded results — channels with one genuine match and channels with twenty both return roughly thirty rows, and the returned rows carry no matched-text snippet. Counts taken this way were off by an order of magnitude in both directions during this build. This was verified against description reads and is a hard rule, not a preference.
**The method that works, and the implementation.** Resolve the channel, enumerate its uploads playlist, read the **full** description of every upload, and regex for the donor brand. Count and date the hits.
This is implemented in `scripts/donor_trail.py` against the YouTube Data API v3, and that script is the canonical implementation. It resolves a handle or URL via `channels.list`, pages the uploads playlist via `playlistItems.list`, and pulls full snippets via `videos.list`. Cost is about **four quota units per channel at depth 90** — two playlist calls and two video calls — so the default 10,000-unit daily allowance covers roughly 2,500 channel scans. The first version of this scan was browser-driven and cost 90 page fetches and about 13 seconds per channel; the API version is the same measurement two orders of magnitude cheaper, and the browser method is retained only as a fallback if API access lapses.
**Full descriptions are non-negotiable.** `vendor/youtube-scout/scripts/scout.py` truncates descriptions to 300 characters, which is fine for its own topic-research job and fatal for this one: sponsor disclosures and promo codes routinely sit past the 300th character, so a truncated read silently undercounts. `donor_trail.py` keeps the untruncated `snippet.description`. Any future refactor that shares code with scout.py must preserve this.
Depth matters and is the main cost driver. A 28-upload window catches only the last few months and returns zero for channels with a real multi-year history; it produced almost nothing on the second discovery wave and is the reason that wave looked empty. **Standard depth is 90 uploads**, which reaches one to three years for most lifestyle channels.
**Two distinct patterns, scored differently.**
*Discrete integrations* — the donor brand appears in a minority of uploads, clustered on specific dates. This is episodic paid booking. The count is the number of times the brand chose to buy again, and it is the signal described in §2. Typical range in this cohort: 2 to 13 out of 90.
*Standing affiliate link* — the donor brand appears in nearly every description because the creator keeps a permanent code block. Observed at 73/90, 78/90 and 90/90. This is a different fact and must not be pooled with the first: it means the creator monetizes the donor brand continuously and their audience is trained to use description links, which is a genuine and arguably stronger transacting signal, but the count is not a count of rebooking decisions. Record the pattern type on the creator record; never report a standing-link count as a sponsorship count.
The separator is the ratio and the date clustering: hits above roughly 60% of scanned uploads, spread evenly across dates, is a standing link. Below roughly 30%, clustered, is discrete. The band between needs a human look.
**The referral-code false positive, and the subscriber floor.** Consumer-subscription donors issue a referral code to *every customer*, so a description match conflates two unrelated facts: the brand paid this creator, and a viewer pasted their own link hoping for free meals. The distinction is invisible in the text — both render as `hellofresh.com/...` in a description.
This did not appear in the 47-channel hand-built run, because that pool was seeded from creators already plausible as sponsorship targets. At 380 channels it dominated the top of the table: of 41 candidates that qualified as "Tier A, discrete, 2+ hits", 37% were under 5,000 subscribers and the highest-ranked included a channel with **23 subscribers** and eleven HelloFresh mentions. No brand books a 23-subscriber channel.
The mitigation is a subscriber floor (`min_subs`, default 10,000) below which matches are reported in a separate audit section rather than ranked. The floor is a heuristic, not a truth: genuine micro-influencer sponsorships exist below it and referral codes exist above it. It is set where the noise stops dominating, and the excluded rows are printed rather than silently dropped so the boundary stays inspectable. A sharper test — whether the description carries a *tracked campaign* link rather than a bare referral code — is the right long-term fix and is not yet implemented.
**Placement format is recorded, and the two formats serve different goals.** `donor_in_longform` and `donor_in_shorts` split each creator's donor placements by video duration (Shorts ≤ 180s, YouTube's ceiling since Oct 2024), and `shorts_share` records what proportion of their output is Shorts. This costs nothing: `videos.list` quota is per call, not per part, so `contentDetails` rides free on the call already being made.
The split matters because Homeaglow buys both against *different objectives*: 60–90 second integrations inside long-form vlogs are the conversion driver, while Shorts are bought for video-pack and SEO ranking. Only long-form placements are scored as conversion evidence; Shorts capability is reported as a capability. This also means the donor signal is stronger than a proxy — HelloFresh's long-form integrations are the same placement, in the same format, sold to the same audience, as the one Homeaglow buys to convert.
**Geography is a first-class filter, applied before scoring, not after.** HelloFresh runs large separate UK, Canadian, Australian and European creator programs, and generic English-language queries surface them preferentially — more than half of the highest-repeat creators found in this build were UK. Homeaglow needs US-heavy audiences, so a creator who fails geography is excluded regardless of sponsorship count. Channel metadata country is frequently absent, so resolve it from content markers in titles and descriptions (currency symbols, retailer names, "mum" versus "mom", place names, and the donor brand's country-specific domain) rather than trusting the profile field.
## 4. Topic derivation — where the candidate pool comes from
The donor scan answers "does this creator carry donor evidence". It does not answer "which creators should we look at", and that prior question decides what the scan can possibly find. Topics live in a study config (`briefs/studies/<brand>-<donor>.json`) so the choice is inspectable and versioned rather than buried in a prompt.
The eight topics in the first Homeaglow study map to the brief this way: family and mom in day-in-life format (`day in the life mom vlog`, `working mom day in my life`, `toddler mom realistic day`), cleaning-adjacent (`clean with me cleaning motivation`, `weekly reset sunday reset`), home management (`home organization declutter`), and two life-stage triggers rather than verticals (`large family costco haul`, `new house homeowner vlog`) on the theory that household load spikes at those moments and that is when a person actually hires a cleaner. The format words are deliberate: vlog and day-in-the-life drove 52.8% of Q1 conversions, and the Jaz Turner archetype — household management where hiring help is a natural on-camera moment — is what the topics are trying to reproduce.
Vocabulary is US-flavoured on purpose (`mom`, `costco`, `target`) because generic English queries preferentially surface the donor's UK program. This is a discovery-side geography lever, distinct from and prior to the screen in §7.
**Three limitations, stated because they bound what any run can find.** First, every topic is prefixed with the donor brand, so the pool is donor-adjacent creators rather than best-fit creators generally: a perfect Homeaglow match who has never worked with HelloFresh is invisible to this method. That is the correct trade for a donor-trail study and the wrong one for a general discovery run. Second, the first study's topics do not cover the brief's Q3 hypothesis verticals (tech/gadget, pets, mail/auto), so a run against these topics cannot satisfy the brief's per-slate coverage requirement and that gap must be sourced separately. Third, the topics are judgment applied to the brief, not derived from data.
**The intended fix for the third.** Once a cohort has measured sign-up rates, derive the next round's topics from the content of the creators who actually converted rather than from a reading of the brief. That closes the loop the product is built on, and it is the first place the engine should start improving itself.
## 5. Scoring changes
PRD §7.3 keeps its six dimensions and its weights. Two changes to how two of them are computed.
**Audience purchase behavior (25) is now evidence-graded rather than binary.** Score it from the donor-trail record: the number of discrete rebookings by the primary donor brand, the presence of a standing link, the count of distinct secondary donor brands, and recency of the most recent donor placement. A creator with six discrete HelloFresh bookings and an Instacart trail scores near the top of this dimension; a creator with one HelloFresh video two years ago scores near the bottom of it.
**Conversion-profile fit (30) gates the donor signal.** The donor count only earns its weight when the content context matches — household management, day-in-the-life, home, family, cleaning, cooking-at-home. Entertainment, gaming, sports and comedy channels with high donor counts score high on purchase behavior and low here, which is correct: they are reach plays with a proven transacting audience, and the brief already treats reach plays as requiring a conversion story or a cheap price. This is what keeps the engine from recommending a sports podcast because HelloFresh bought it 114 times.
**Recency is a weight, not a filter.** A donor relationship that last ran in 2019 is real evidence that the donor once converted there, and no evidence about today: rosters churn, audiences turn over, and a lapsed relationship may have lapsed because it stopped working. In the first API run, 71% of nominal Tier A candidates had no donor placement since before 2026, several last running in 2019, and raw hit count ranked them above current relationships. Score therefore multiplies long-form placements by a recency weight — same year 1.0, one year 0.7, two years 0.45, older 0.25. Weighting rather than filtering keeps a deep historical relationship visible while a current one outranks it.
**Projected CPA is reported at the lane level, not invented per creator.** Since CPA = CPM ÷ (10 × sign-up rate), at the brief's $80 CPM cap every creator's projected CPA is $286 at the 0.028% lane median and $80 at the 0.10% optimistic rate. Per-creator CPA becomes real only once a rate card is in hand, and quoting one before that is false precision. The longlist therefore reports the lane math plus each creator's donor evidence, and per-creator CPA is filled in at the rate-request stage.
## 6. Data model additions
Add to `data/creators.csv`:
- `donor_brands` — semicolon-separated donor brands with evidence.
- `donor_primary_count` — discrete rebookings by the primary donor brand.
- `donor_pattern` — `discrete` | `standing` | `mixed` | `none`.
- `donor_scanned` — uploads scanned, so a count is always read as a ratio.
- `donor_window` — how far back the scan reached.
- `donor_last_seen` — recency of the most recent donor placement.
- `geo_verdict` and `geo_basis` — resolved country and how it was resolved.
- `donor_in_longform` / `donor_in_shorts` — donor placements split by format; long-form carries the conversion score.
- `shorts_share` — proportion of scanned uploads at or under 180s, as a capability signal for the SEO/video-pack objective.
New file `data/donor-scans.csv`, one row per channel per scan: handle, scan date, donor brand, scanned depth, hit count, pattern, and the hit dates. Rescanning is cheap and the history is what lets the correlation in PRD §10 be computed later against something other than a point-in-time count.
## 7. Architecture
Scout gains a `donor-trail` mode implementing §3, and the discovery half of Scout is now built on **youtube-scout** (MIT, Daniel Agrici), vendored at `vendor/youtube-scout/` at a pinned commit and installed as the `/scout` skill.
The two halves divide cleanly, and the division is the point:
| Stage | Tool | Job |
| --- | --- | --- |
| Candidate generation | `/scout <topic>` (youtube-scout) | Topic search via YouTube Data API, ranked by views / engagement / momentum / breakout, with a Channels sheet. Replaces the hand-run query waves. |
| Donor scan | `scripts/donor_trail.py` | Channel-scoped, full-description donor counting per §3. Takes `--from-scout <workbook>` to read the Channels sheet directly, or an explicit handle list. |
| Scoring | Assessor | §4 weights against the scan output. |
| Orchestration | `scripts/run_study.py` | Runs the whole chain from one study config: every topic through scout, merge and screen the candidates, donor scan, ranked report. |
Sequence: `/scout` across every topic → merge and de-duplicate → **brand-owned and geography screen** → `donor_trail.py` at depth 90 → report → Assessor scores → shortlist. The screens sit before the scan because the scan is the stage that costs quota; a channel scout has already labelled as British is roughly four wasted units and several wasted seconds.
**The geography screen, and why unknown is not excluded.** Scout returns `Channel Country` for free, so the screen is nearly costless. `geo_prefilter` in the study config takes a `target` and a `keep_unknown` flag. Channels whose metadata names a country other than the target are dropped. Channels with **no** country are kept, because that field is frequently unset by genuine US creators — Ashley Taylor, the strongest pick of the first hand-built run, is one of them — and dropping them would systematically lose exactly the small-to-mid creators the thesis favours. Unknown-country channels then have geography resolved from content markers during the scan (§3), so they earn inclusion rather than being assumed in. On the first Homeaglow pool this dropped 75 of 457 (GB 32, CA 21, AU 6, tail 16) and kept 380 (292 US plus 88 unknown).
The report applies the geography split again at the end, so anything the prefilter let through on an unset field still cannot reach a Tier A table without a resolved verdict.
Both tools share one API key, resolved identically (`YOUTUBE_API_KEY`, then `SCOUT_ENV_FILE`, then `~/.config/scout/.env`, then `./.env`) and never printed or copied into the repo. Combined quota for a full slate run — one topic scout at 50 videos plus 50 channel scans at depth 90 — is roughly 300 units against a 10,000/day allowance.
Everything stays inside the compliance rule already in `CLAUDE.md`: official API and public platform data only, no credentialed scraping, no PII beyond public business contact. No third-party sponsorship database is required. The paid databases were checked during this build and their public tiers report aggregate counts that do not separate standing links from discrete bookings and do not resolve geography, which is why the scan is built rather than bought.
**Why youtube-scout rather than rolling our own discovery.** It already does quota accounting, pagination, retry and backoff, comment and caption extraction, and a workbook writer, all of which Bellwether would otherwise have to write and maintain. It is MIT, has tests and CI, and its `--into` flag appends to an existing workbook, which fits the existing scorecard workflow. Vendoring at a pinned commit keeps runs reproducible; `vendor/youtube-scout/VENDORED-COMMIT.txt` records the commit and re-vendoring is a deliberate act, not a silent upstream pull.
## 8. Running it
```javascript
# one-time: key (YouTube Data API v3, restricted to that API)
mkdir -p ~/.config/scout && printf 'YOUTUBE_API_KEY=YOUR_KEY\n' > ~/.config/scout/.env
chmod 600 ~/.config/scout/.env

# the whole study, one command
python3 scripts/run_study.py --study briefs/studies/homeaglow-hellofresh.json

# resume after any interruption: reuses cached scout workbooks (the expensive
# part, 100 units per search call) and skips channels already scanned today
python3 scripts/run_study.py --study briefs/studies/homeaglow-hellofresh.json --skip-scout

# individual stages, when needed
/scout hellofresh day in the life mom vlog --max 100 --sort breakout
python3 scripts/donor_trail.py --channels @AshleyTaylorr,@rachelleea --dry-run

```
`--dry-run` prints the ranked table and writes nothing. Rows append with the scan date, so rescans build history rather than overwriting it.
**Resumability is a hard requirement, not a nicety.** A full study is a few thousand API calls over fifteen to thirty minutes, which is long enough that a transient network fault is likely rather than possible — the first Homeaglow API run died on a socket timeout at channel 350 of 455. Three properties follow, and any future rewrite must keep them:
1. **Checkpoint per channel.** Each row is written and flushed the moment it is scanned. A crash at channel 400 keeps 399. The first version wrote the CSV only at the end and lost all 350.
2. **A single channel must not end the run.** Network faults raise a recoverable error the loop catches, skips, and retries in a second pass at the end. Only two conditions are genuinely fatal: exhausted quota and an invalid key.
3. **Resume by exact input reference, scoped to the day.** Every row records the `source_ref` it came from; a re-run skips references already scanned *today*. Scoping to today means a monthly re-run refreshes rather than skips. Ctrl-C is safe and says so.
Retries are six attempts with backoff capped at 30 seconds, on a 45-second timeout.
**Quota.** Scout costs 100 units per search call (50 results); everything else costs 1 per call. A full eight-topic study at `--max 100` is roughly 1,600 units for discovery plus about 4 per channel scanned — call it 3,000 to 3,500 against the 10,000/day default. Quota resets midnight Pacific, and an exhausted-quota exit is safe to resume from the next day.
## 9. Known limits
The scan reads descriptions only, so a verbal-only sponsorship with no description link is invisible and the counts are a floor rather than a total. A description match cannot currently distinguish a paid placement from a customer referral code, which the subscriber floor mitigates without solving (§3). Depth 90 truncates long-running channels, so a high-upload-frequency creator's window is shorter in months than a low-frequency one's — the `donor_window` field exists so this is visible rather than silently distorting comparisons. Donor-brand rebooking reflects the donor's economics, not Homeaglow's, and the two diverge where the price points or purchase frequencies differ sharply. The candidate pool is bounded by the topics (§4), so the method cannot surface a creator its topics never reach, and donor-prefixed topics cannot surface a good-fit creator who has never worked with the donor. And the whole thesis is still unproven until the bake-off readout; this spec makes the signal measurable, it does not make it true.
## 10. Operational lessons
Recorded because each one cost real time on the first build, and the next person (or the next session) should not rediscover them.
**Counting from the wrong surface.** Two false sources of sponsorship counts were tried and rejected before the current method: YouTube's channel-search page (pads to ~30 rows regardless of true matches) and scout.py's `Description` column (truncates at 300 characters, past which most sponsor disclosures sit). Both produce numbers that look plausible and are wrong. §3 is the rule.
**Scale surfaces false positives that a hand-picked pool hides.** The referral-code problem (§3) was invisible across 47 seeded channels and dominant across 380. Any signal validated on a curated sample should be re-validated the first time it runs unseeded, and the first large run should be read as a test of the method rather than as a result.
**Geography is the dominant confound in this category.** More than half the highest-repeat creators found by generic English queries were UK. Donor brands of this type run large separate national programs, and nothing in a sponsorship count reveals which program a creator belongs to. Geography is handled at three points — topic vocabulary (§4), pre-scan screen (§7), and post-scan resolution (§3) — and that redundancy is deliberate.
**The scan is long enough that resumability is a correctness property**, not an optimisation. See §8.
**Credentials and network are separate problems, and network was the binding one.** The API key belongs in `~/.config/scout/.env` at `chmod 600`, outside any synced or version-controlled folder, and is read by both tools through the same resolution order. Note that an agent session's shell may not be able to reach `googleapis.com` at all: egress is allow-listed per organization, and during this build both the cloud container and the on-device VM were refused with `403` on `CONNECT` to `www.googleapis.com` while GitHub and PyPI passed. So the study may have to be run from the operator's own terminal regardless of where the key sits. Test reachability before moving a secret anywhere.
**Do not paste a key anywhere it will be stored.** Edit the env file in place, keeping the `YOUTUBE_API_KEY=` prefix, or write it with a shell `read -s`. Verify with `grep -c '^YOUTUBE_API_KEY=AIza' <file>`, which answers yes or no without printing the value. A key that does reach a transcript or a log is compromised and should be deleted in the console and reissued, whatever its restrictions.
**Key restrictions: set API restriction, not application restriction.** These scripts call Google server-side and send no `Referer`, so an HTTP-referrer ("websites") restriction blocks every request. Application restrictions must be *None*; the API restriction to YouTube Data API v3 is the one that actually contains the blast radius.
## 11. Success criteria for this spec
Inherited from the bake-off: agent-sourced creators post a median sign-up rate at or above 0.05% against the 0.028% baseline. Specific to the donor signal: within the agent arm, creators with three or more discrete donor bookings should outperform creators with zero or one on measured sign-up rate. If they do not, the donor trail is not the signal and the weight in §4 comes back out.
